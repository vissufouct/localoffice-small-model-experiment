# Result logs: experiment, not a product scorecard

These CSVs make included successes and failures inspectable. They are generated by `scripts/export_result_csvs.py` from public redacted JSON evidence and explicitly labelled validation summaries. This is a curated subset, not a complete export of the development session.

| File | Rows / unit | Meaning of PASS |
|---|---|---|
| complete_task_runs.csv | 1 complete task | Full acceptance; the included run failed |
| drafting_diagnostic.csv | 8 drafting responses | Semantic review against that case's complete objective; no document/task acceptance |
| scope_diagnostic.csv | 6 scope selections | Exact expected source span, independent of draft quality |
| completion_diagnostic.csv | 3 completion selections | Selection of finish; all three failed, no actions executed |
| validation_summary.csv | 4 validation summaries | Engineering/build/UI check only; never model accuracy |

Fields include criterion, outcome, source and available usage/timing. `NOT_ASSESSED` is distinct from failure. Empty measurements mean unavailable/not applicable, never zero. Sources are relative to this directory. Review assessments are recorded judgements by Codex, not independent blinded labels. Portuguese operator-counterfactual rows are explicitly labelled; they cannot measure model selection accuracy. Historical cohorts and verifier versions must not be pooled. Test counts across selections may overlap.

Public JSON wraps the original redacted content under `data`. Historical hashes inside evidence identify originals; package-manifest hashes identify exported bytes. Some raw historical reports and saved-state databases are intentionally not included. Neither a CSV pass nor an exit-zero machine check replaces semantic, rendered visual and lifecycle acceptance.
